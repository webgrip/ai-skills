# Writes, approvals and operator surfaces

An MCP App that changes something is an operator console inside a chat. The host's approval card, the button state and `visibility: ["app"]` are conveniences; the server is the only control.

## The confirmed write

```
view                     host                          server
 |-- Restart ------------>| tools/call prepare ---------->| authorize(principal, action, target)
 |                        |                               | mint token {principal, target, expiry}, single use
 |<-- summary + token ----|<------------------------------| token in result _meta, summary in structuredContent
 |-- Confirm (+ idempotency key) ---- tools/call confirm ->| idempotency hit? return first receipt as duplicate
 |                        |                               | token valid, same principal, same target, unexpired?
 |                        |                               | authorize again, act, audit
 |<-- receipt ------------|<------------------------------| { operationId, outcome }
```

Rules, all enforced in the template's [server.ts](template/server/ts/server.ts) and covered by [server.spec.ts](template/tests/server.spec.ts):

- **Authorize on every call**, prepare and confirm, for the principal of this request. A permission shown in `structuredContent` (`actions.restart.allowed`) only decides whether a button renders.
- **Token**: random, bound to principal and target, single use, short expiry (minutes). It goes in result `_meta`, not in `structuredContent` or `content`.
- **Idempotency key**: generated by the view once per confirmation (`crypto.getRandomValues`, which works without a secure context), scoped per principal on the server; a replay returns the first receipt marked `duplicate`.
- **Summary says exactly what will happen** ("Restart all 3 replicas of Checkout API (v2.8.1) one at a time"), rendered in a `role="status"` region, with focus moved to the confirm button and returned to the trigger on cancel.
- **Optimistic UI**: show "requested" at once, then reconcile with the receipt or the error text; never show success before the receipt.
- **Audit** every accepted write as structured log: principal, action, target, operation id, time. stdio servers log to stderr.
- **Few app tools.** Some hosts ask the user to approve each app tool separately; one `prepare` plus one `confirm`, or one tool with an `action` enum, beats a tool per button.
- **Tell the model**: after a write, `updateModelContext` with one sentence when the host offers it, so the next turn does not contradict the screen.

## Operator surface patterns

| Surface | Shape | Notes |
|---|---|---|
| Status card | inline, read-only, one action | the template |
| Approval queue | inline list of 3-8 pending items, approve and reject per item, each through prepare/confirm | reject reason is chat text, not a form in the card |
| Runbook step | inline card per step: precondition check result, the exact command or API call as a summary, confirm | the server runs the step; the view never holds credentials |
| Dashboard | fullscreen, read-only panels, refresh through an app-only read tool | refresh is idempotent and rate-limited server side |
| Incident console | fullscreen; timeline plus a small set of confirmed actions | every action audited with the incident id |

## Least privilege

- The view only calls tools of its own server, through the host. It holds no tokens and fetches nothing directly; with an empty CSP it cannot.
- Read and write stay separate tools with explicit `readOnlyHint` and `destructiveHint` (see the mcp-server skill for annotations and scopes).
- Separate who may *see* from who may *act*: the read tool filters by the caller; the write tools re-check.
- Rate-limit and size-cap app tools like any other tool input; the view is attacker-influenced too.
- High-impact actions (data deletion, money, production config) need an out-of-band approval or a second person, not only a confirm button.
