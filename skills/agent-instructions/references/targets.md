# Choosing targets

Step 2 of [Set up a repo](../SKILL.md#set-up-a-repo): enable only the tools the team uses, per
category. This file says which and why; what each tool reads is in [tools.md](tools.md). A target
id is the `id` of its entry in [assets/targets.json](../assets/targets.json).

## Enabling a target

`agent_setup.py layout` writes `.ai/agent-setup.json` with the detected targets (or
`--targets a,b`; `claude-code` is always included). Edit the `targets` list to match what the team
uses, then run `generate`. The other keys override `defaults` in targets.json (`token_budget`,
`rule_line_limit`, `agents_md_max_bytes`, `bytes_per_token`, the directories):

```json
{
  "targets": ["claude-code", "codex", "cursor", "copilot", "coderabbit", "github-actions", "lefthook"],
  "token_budget": 5200
}
```

- `generate` and `check` act only on enabled targets. Detection finds files, not habits: a tool
  someone uses without leaving a file in the repo is still a target, and a stale `.cursorrules` is
  not.
- **Disabling a target**: pruning only touches enabled targets, so remove the id and then delete
  the files `generate` wrote for it by hand (each carries a `<!-- Generated by agent_setup.py`
  line).
- `AGENTS.md` alone already reaches most agents. Enable a tool to get its path rules, skills
  directory, MCP file or setup file, not to make it read instructions.

## Interactive agents

Ranked by the [Stack Overflow survey](https://survey.stackoverflow.co/2026/ai/data/ai-code-agent)
and the [JetBrains adoption study](https://blog.jetbrains.com/research/2026/08/ai-coding-agent-adoption-2026/).

| Tool (id) | Enable when | Gets |
|---|---|---|
| Claude Code (`claude-code`) | anyone uses it, CLI or IDE | `CLAUDE.md` = `@AGENTS.md`; symlinks `.claude/rules` → `../.ai/rules` and `.claude/skills` → `../.agents/skills`; `.claude/settings.json` and `.mcp.json` by hand (step 7) |
| GitHub Copilot (`copilot`) | anyone uses Copilot in an editor or CLI | generated `.github/instructions/<rule>.instructions.md` (`applyTo`); `.vscode/mcp.json` or `.mcp.json` for MCP; `copilot-instructions.md` only for Copilot-only lines |
| OpenAI Codex (`codex`) | anyone uses Codex CLI, IDE or app | nothing generated: `AGENTS.md` with the `.ai/rules` pointer line, kept under 32 KiB; `.codex/config.toml` only for MCP |
| Cursor (`cursor`) | anyone uses Cursor | generated `.cursor/rules/<rule>.mdc` (`globs`, `alwaysApply: false`); `.cursor/mcp.json` for MCP; `.cursorrules` deleted |
| Google Antigravity (`antigravity`) | anyone uses Antigravity or `agy`, or used Gemini CLI on a personal account | generated `.agents/rules/<rule>.md` (`trigger: glob`); `.agents/mcp_config.json` for MCP |

Runners-up: OpenCode (`opencode`: nothing generated; `opencode.json` for MCP and permissions),
JetBrains Junie (`junie`: nothing generated, no path-rule format; never a `.junie/AGENTS.md`, which
hides the root file), Devin Desktop, formerly Windsurf (`devin-desktop`: generated
`.devin/rules/<rule>.md` with `trigger: glob`; its glob list format is inferred, so confirm with a
probe), Warp (`warp`: nothing generated; delete `WARP.md`), Cline (`cline`: generated
`.clinerules/<rule>.md` with a `paths:` list). Further out: Kiro (`kiro`: generated
`.kiro/steering`), JetBrains AI Assistant (`jetbrains-ai-assistant`: no path-rule format), Zed
(`zed`: `AGENTS.md` with every leftover deleted), Gemini CLI (`gemini-cli`: only for Code Assist
Standard/Enterprise or API-key users, with `context.fileName` naming `AGENTS.md`).

## Cloud agents

Enable the cloud agents the team hands work to. Each reads `AGENTS.md`; what it needs beyond that
is mostly a setup file written by hand. Setup, triggers, identity and network per agent:
[unattended.md](unattended.md).

| Agent (id) | Enable when | Gets |
|---|---|---|
| Claude Code cloud sessions, routines and Action (`claude-code`) | anyone starts Claude Code in the cloud or with `@claude` | the interactive files; a `SessionStart` hook that installs dependencies when `CLAUDE_CODE_REMOTE=true` (setup script and network live in the UI environment); the Action workflow by hand |
| Cursor cloud agents (`cursor-cloud-agents`) | anyone hands work to Cursor's cloud | the generated `.mdc` rules; `.cursor/environment.json` by hand |
| Copilot cloud agent (`copilot-cloud-agent`) | issues get assigned to Copilot | the generated `.github/instructions`; `.github/workflows/copilot-setup-steps.yml` by hand |
| Codex cloud (`codex-cloud`) | anyone runs Codex tasks in the cloud | nothing beyond `AGENTS.md` and skills: the environment lives in ChatGPT |
| Devin (`devin-cloud`) | the team delegates to Devin | `AGENTS.md` (the first 16 KiB of each is read) and `.agents/skills`; `.devin/blueprint.yaml` by hand |

Runners-up: Google Jules (root `AGENTS.md` only; setup in its UI), Amp (`.agents/setup`), OpenHands
(`openhands`: `.openhands/setup.sh`, `.openhands/hooks.json`), Factory, GitLab Duo Agent Platform
(`.gitlab/duo/agent-config.yml`; the only agent native to GitLab). Forgejo and Gitea have none:
run a headless CLI in a runner ([unattended.md](unattended.md#triggers-identity-network-forges)).

## Review bots

Run one bot on every change; the rules for any bot and the per-bot detail are in
[review-bots.md](review-bots.md).

| Bot (id) | Enable when | Gets |
|---|---|---|
| GitHub Copilot code review (`copilot-code-review`) | the repo is on GitHub and has Copilot | the generated `.github/instructions` (shared with `copilot`); a ruleset turns review on |
| CodeRabbit (`coderabbit`) | config as code is wanted, or the repo is on GitLab, Bitbucket or Azure DevOps | the `{files, applyTo}` block `generate` keeps in its config |
| OpenAI Codex code review (`codex-code-review`) | the team works in ChatGPT and Codex | a `## Code Review Rules` section in `AGENTS.md`, by hand |
| Cursor Bugbot (`cursor-bugbot`) | the team uses Cursor | `.cursor/BUGBOT.md` by hand; the generated `.mdc` rules do not reach it |
| Greptile (`greptile`) | self-hosting or Gitea is needed | `.greptile/config.json` with scoped `rules[]`, by hand |

Runners-up: Sourcery (dashboard only), Claude Code Review (`REVIEW.md` and nested `CLAUDE.md`), Qodo
(`qodo-merge`: `.pr_agent.toml`), cubic (`cubic.yaml`), Devin Review. Gemini Code Assist
(`gemini-code-assist`) and GitLab Duo Code Review sit just outside. On Forgejo and Gitea only
Greptile Enterprise and the open-source PR-Agent review ([review-bots.md](review-bots.md#forges)).

## Generators

A generator already in the repo is a co-tenant: enable it so `inventory`, `generate` and `check`
leave its markers and output alone. The per-tool rule fan-out is `agent_setup.py generate`; do not
add a second fan-out tool.

| Tool (id) | Enable when | Gets |
|---|---|---|
| Laravel Boost (`laravel-boost`) | `laravel/boost` is a dependency | its block in `AGENTS.md`, `.ai/rules/index.md` and `.ai/rules/boost/` left alone; skills sourced from `.ai/skills`; the drift job in [generators.md](generators.md#ci-drift-check) |
| Nx (`nx`) | `nx.json` exists | its `AGENTS.md` block left alone; `nx configure-ai-agents --check` in CI |
| Symfony AI Mate (`symfony-ai-mate`) | `symfony/ai-mate` is a dependency | its `AGENTS.md` block left alone |
| rulesync (`rulesync`) | it already owns the repo's rules | a migration decision first: it strips top-level `paths:` and makes `AGENTS.md` an output |
| Ruler (`ruler`) | it already owns the repo's rules | a migration decision first: it flattens rules to always-on text and gitignores its output |

Runners-up: Next.js and rails-ai-context (marked blocks, [generators.md](generators.md#other-generators)),
APM and ai-rulez (faithful glob mapping, but their own source tree).

## CI forges

Enable the forge the repo's pipeline runs on. Each gets one job that runs `check` in a small Python
image; snippets and the caveats that bite are in [ci.md](ci.md).

| Forge (id) | Gets |
|---|---|
| GitHub Actions (`github-actions`) | a workflow on `pull_request`, `push` and `merge_group` ([ci.md](ci.md#github-actions)) |
| GitLab CI/CD (`gitlab-ci`) | a job in MR and branch pipelines ([ci.md](ci.md#gitlab-ci)) |
| Forgejo Actions (`forgejo-actions`) | a workflow in a node image that has Python ([ci.md](ci.md#forgejo-actions)) |
| Bitbucket Pipelines (`bitbucket-pipelines`) | a step in `pull-requests` and the main branch ([ci.md](ci.md#bitbucket-pipelines)) |
| Azure Pipelines (`azure-pipelines`) | a script step, or a build-validation policy on Azure Repos ([ci.md](ci.md#azure-pipelines)) |

Runners-up (CircleCI, Jenkins, Woodpecker, Buildkite): one shell step running the same command.

## Hook managers

Use the manager the repo already has; never add a second. With none, pick by stack: lefthook (any
stack, one binary), husky for Node, pre-commit for Python, CaptainHook for PHP. Each gets a
pre-commit and a pre-merge-commit hook running `check` ([ci.md](ci.md#pre-commit-hooks)).

| Manager (id) | Gets |
|---|---|
| lefthook (`lefthook`) | jobs in `lefthook.yml` with `glob_matcher: doublestar` |
| husky (`husky`) | `.husky/pre-commit` and `.husky/pre-merge-commit`, with lint-staged or the shell guard |
| pre-commit (`pre-commit`) | a `repo: local` hook in `.pre-commit-config.yaml` |
| CaptainHook (`captainhook`) | an action with a `FileStaged\Any` condition in `captainhook.json` (no merge hook) |
| simple-git-hooks (`simple-git-hooks`) | the shell guard in `package.json` |

Runner-up: plain git hooks in a committed `.githooks/` with `core.hooksPath` set per clone.

## Adding a tool

1. Read the tool's own docs for: instruction files, the path-rule directory, extension and
   frontmatter keys, the glob syntax (YAML list or comma string, quoted or not, anchored where),
   what happens to a rule without frontmatter, skills directories, MCP file, ignore file, hooks.
   Source globs are anchored at the repo root (`*.php` matches root files only, `**/*.php` any
   depth); a tool that anchors differently needs that translated.
2. Add one entry to [assets/targets.json](../assets/targets.json), copying the closest existing
   entry: `id`, `name`, `category`, `detect`, `instructions`, `rules`, `skills_dir`, `mcp_config`,
   `setup_file`, `docs`.
3. If its path rules match an existing format (`claude-symlink`, `cursor-mdc`, `copilot-applyto`,
   `trigger-globs`, `kiro-filematch`, `cline-paths`, `coderabbit-filepatterns`), set
   `rules.format` to it and stop: the entry is the whole change. A tool without path scoping gets
   `"rules": null`.
4. Only a new path-rule format needs a new formatter in `scripts/agent_setup.py`, keyed by that
   `rules.format`.
5. Add its row to [tools.md](tools.md), run `generate` on a scratch repo, and probe the tool once to
   see a generated rule load for a matching file.
